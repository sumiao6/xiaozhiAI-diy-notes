# 第二章　代码结构与改动清单

> 这一章回答三个问题：**代码放在哪、改了哪些文件、为什么这么改。**
> 想改造项目的人，先读完这一章再动手，否则很容易改错地方。

---

## 2.1 你只需要关心这一个目录

整个 xiaozhi-esp32 工程很大（几十种板型、上百个文件），但本项目只动了一处：

```
xiaozhi-esp32/
└── main/
    ├── boards/
    │   ├── bread-compact-wifi/          ← 本项目的全部改动都在这里
    │   │   ├── config.h                 ← 所有引脚和参数
    │   │   ├── compact_wifi_board.cc    ← 板型入口（实例化外设）
    │   │   ├── led_strip_controller.h   ← 新增：彩灯板
    │   │   ├── dc_motor_controller.h    ← 新增：直流电机 + 差速
    │   │   ├── pca9685_servo.h          ← 新增：PCA9685 舵机
    │   │   └── servo_controller.h       ← 旧版 LEDC 直驱舵机（已停用，留作参考）
    │   └── common/                      ← 官方公共代码（Button 类在这里）
    ├── display/                         ← 屏幕（本项目未改）
    ├── mcp_server.cc                    ← MCP 协议实现（未改）
    └── application.cc                   ← 应用主逻辑（未改）
```

**为什么只动一个目录**：这是这个工程最好的设计。板型之间互不干扰，你改坏了 `bread-compact-wifi`，别的板型照样能编译。

## 2.2 板型是怎么被"选中"的

三件事串起来：

1. `menuconfig` 里选 `Xiaozhi Assistant → Target Board = Bread Compact Wi-Fi (面包板)`，屏幕另在 `OLED Type` 选 `SSD1306 128*64`
2. `main/CMakeLists.txt` 用 `file(GLOB boards/${BOARD_DIR}/*.cc)` 把该目录下所有 `.cc` 编进去
3. 每个板型文件末尾有一行 `DECLARE_BOARD(CompactWifiBoard);`，把自己注册到板型工厂

**对改造者的实际意义**：

> **新增一个 `.h` 头文件，不需要改任何构建脚本。**
> 因为它是 header-only，只要被 `.cc` `#include` 进来就参与编译。把文件丢进目录、加一行 include，就完事了。

只有**新增 `.cc` 源文件**才需要考虑 CMake，本项目没这个需求。

## 2.4 `InitializeTools()` 现在长什么样

这是整个项目的中枢，一共不到 40 行：

```cpp
void InitializeTools() {
    // 板载单色小灯（GPIO18）。有了彩灯板后两个都叫"灯"会分不清，停用。
    // static LampController lamp(LAMP_GPIO);

    // ① 舵机通道表：一行一路，加舵机就是加一行（实际 11 行，通道 0~10）
    static const ServoChannelDef kServoChannels[] = {
        { 0, "1号", false, SERVO_PULSE_MIN_US, SERVO_PULSE_MAX_US },   // 180°，实物接了
        { 1, "2号", false, SERVO_PULSE_MIN_US, SERVO_PULSE_MAX_US },   // 180°，空着
        // ... 3~8 号同构，占通道 2~7（都是给 180° 预留的空位）
        { 8, "9号",  true,  SERVO_PULSE_MIN_US, SERVO_PULSE_MAX_US },  // 360°，实物接了
        { 9, "10号", true,  SERVO_PULSE_MIN_US, SERVO_PULSE_MAX_US },  // 360°
        { 10, "11号", true, SERVO_PULSE_MIN_US, SERVO_PULSE_MAX_US },  // 360°
    };
    constexpr int kServoCount = sizeof(kServoChannels) / sizeof(kServoChannels[0]);

    // ② 一行创建一个舵机总线（管全部舵机，只占 4 个工具）
    static Pca9685ServoBus servo(SERVO_I2C_SDA, SERVO_I2C_SCL,
                                 kServoChannels, kServoCount,
                                 PCA9685_ADDR, "servo",
                                 PCA9685_PWM_HZ, PCA9685_OSC_HZ);

    // ③ 一行创建彩灯板
    static LedStripController light(LED_STRIP_GPIO, LED_STRIP_MAX,
                                   "light", "彩灯板", LED_STRIP_COUNT);

    // ④ 一行一个电机
    static DcMotor motor1(MOTOR1_IN1, MOTOR1_IN2, "motor1", "1号电机", MOTOR1_INVERT);
    static DcMotor motor2(MOTOR2_IN1, MOTOR2_IN2, "motor2", "2号电机", MOTOR2_INVERT);

    // ⑤ 一行创建电机组（把两个电机交给它）
    static CarController car(motor1, motor2, "car", "小车");
}
```

> 最后那个 `"小车"` 是给模型看的中文标签，固件里的类名是 `CarController`，日志也打印 `Car: 小车(car)`。它做的只有一件事：**把两个电机当成一组来协调**（同时正转、一快一慢转向、反向旋转）。没有车架、不装轮子，这套代码照样跑。

> 上面为了省篇幅，把通道 2~7 的 6 行压成了一行注释。**完整 11 行**见 `代码/compact_wifi_board.cc` 第 161~172 行（`代码/` 与工程里的文件是同一份，可直接对照）。

**这就是"一行创建"的全部秘密**：构造函数里干完了四件事——分配硬件资源、初始化驱动、注册 MCP 工具、启动后台任务。调用方不需要知道任何细节。

## 2.5 一个外设的完整生命周期

以彩灯板为例，`new LedStripController(...)` 这一行内部发生了什么：

```
构造函数
 ├─ 1. 建 NVS 命名空间（"led_" + name），读一次灯珠数量
 ├─ 2. 初始化 RMT 驱动（分辨率 10MHz，缓冲区 64 颗）
 ├─ 3. 注册 5 个 MCP 工具（power / set_brightness / set_color / set_effect / get_status）
 └─ 4. xTaskCreate 起一个 30fps 的渲染任务
        ↓
    任务循环：每 33ms 读一次状态变量 → 算出每颗灯珠颜色 → refresh
        ↓
    语音回调：只改状态变量（power_ / brightness_ / base_r_ ...），立刻返回
```

> **第 1 步现在只剩"读"**：早期有个 `set_led_count` 工具会把数量写进 NVS，这个工具已经删掉了——灯珠数改成在 `config.h` 里设（见 3.11），不再占一个工具名额。
> 于是代码里 `settings.GetInt("count", active_)` 读到的，只可能是**旧固件当年留下的值**。这也是个隐藏的坑：如果改了 `config.h` 却发现灯珠数没变，先清一次 NVS（`idf.py -p COM15 erase-flash` 再重烧），别怀疑代码。

**关键设计：语音回调和渲染是分离的。**

- 语音回调跑在 MCP 的线程里，**必须极快返回**。里面只要有一个 `vTaskDelay(1000)`，整个语音响应就会卡住，用户会觉得"小智死了"。
- 所以回调只写变量，真正刷硬件在独立任务里做。
- 变量用 `volatile` 修饰，防止编译器把"只写不读"的变量优化掉。

同样的模式在电机（`DcMotor` 没有后台任务，但用 `esp_timer` 做超时）和舵机（`Pca9685ServoBus` 用互斥锁保护 I2C）里都有体现。

## 2.6 MCP 工具：让大模型"看见"你的硬件

### 工具是什么

大模型不知道你的板子上有灯。它只知道一份"工具清单"，清单里每一条告诉它：**能做什么、叫什么名字、要传什么参数**。

```cpp
auto& mcp_server = McpServer::GetInstance();   // ← 先拿到全局实例，每个 controller 里都是这一句

mcp_server.AddTool(
    "self.light.power",                    // ① 工具名（英文，全局唯一）
    "打开或关闭彩灯板。on 传 true 是开灯，false 是关灯。",   // ② 描述（给模型看的）
    PropertyList({                          // ③ 参数表
        Property("on", kPropertyTypeBoolean, true)
    }),
    [this](const PropertyList& properties) -> ReturnValue {   // ④ 实际执行的 C++ 代码
        power_ = properties["on"].value<bool>();
        return true;
    });
```

### 四个要素，缺一不可

| 要素 | 作用 | 写错的后果 |
|---|---|---|
| **工具名** | 模型调用时的标识 | 重名会被**丢弃**，而且不报错——串口只留一条 `Tool ... already added` 的 W 级警告，后注册的那个就不存在了 |
| **描述** | 模型决定"什么时候用它"的唯一依据 | 写得太含糊，模型会选错工具，或者干脆不调用 |
| **参数** | 告诉模型要传什么、范围多少 | 范围写错，模型可能传越界值（虽然代码里还要再夹一次） |
| **回调** | 真正干活的 C++ | 阻塞会卡住整个语音链路 |

### 描述为什么重要

看这两条的差别：

```cpp
// ❌ 模型不知道什么时候该用
"控制灯"

// ✅ 模型知道用户说这些话时该调用
"打开或关闭彩灯板。on 传 true 是开灯，false 是关灯。"
"用户说“开灯”“打开彩灯”“亮起来”传 true；"
"说“关灯”“把灯关掉”“灭了”传 false。"
```

第二条里把用户可能说的原话都列进去了。这是"工具描述"能显著提升识别率的实际技巧，不是什么玄学。

### 参数类型

```cpp
Property("speed",     kPropertyTypeInteger, 5, 1, 10)   // 默认 5，范围 1~10
Property("on",        kPropertyTypeBoolean, true)       // 默认 true
Property("color",     kPropertyTypeString,  "red")      // 默认 "red"
```

**参数范围的三个数字**（默认值、最小、最大）不只是给模型看的提示，也是它生成参数时的约束。

## 2.7 32 个工具的上限：本项目最重要的一课

### 报错现场

```
the number of tools has reached limit: 32
```

这是**服务端硬限制**，不在你的固件里，改代码没用。板子能把工具都发上去，服务端只认前 32 个。

### 怎么算出来的

| 来源 | 数量 | 具体是哪些 |
|---|---|---|
| 系统内置 | 2 | `self.get_device_status`（查状态）、`self.audio_speaker.set_volume`（调音量） |
| 自建 | 19 | 灯板 5 + 两个电机各 3（共 6）+ 电机组 4 + 舵机 4 |
| **合计** | **21 / 32** | 还剩 **11 个名额** |

> **系统工具的数量随配置变**，都在 `main/mcp_server.cc` 里注册：有背光的 LCD 屏会多一个 `self.screen.set_brightness`，开了 LVGL 主题会多一个 `self.screen.set_theme`，接了摄像头会多一个 `self.camera.take_photo`。
> 本项目是 **OLED（没有背光）+ 没开 LVGL + 没摄像头**，所以只有 2 个。数自己板子上的工具时，以实际注册结果为准。

### 合并前，自建部分曾经到过 45 个

早期是"一个动作一个工具"的写法，45 个自建工具直接顶爆了 32 上限。几个典型模块：

| 模块 | 合并前 | 合并后 | 怎么合的 |
|---|---|---|---|
| 彩灯板 | 8 | **5** | `turn_on` + `turn_off` → `power(on)` |
| 电机组 | 11 | **4** | 各种动作 → `move(action, level, seconds)` |
| 舵机 | 每路一套（8 路 × 2~3 个） | **4** | 全部舵机共享 `set_angle(id, angle)` |
| 电机 | 6 | 6 | 本来就是 `run/speed/stop` 三个 |

前三个模块 8 + 11 + 6 = 25 个，剩下约 20 个是当时给每路舵机单独配的指令，以及后来直接删掉的小功能（比如用工具改灯珠数量的 `set_led_count`）。

> **口径说明**：这里的 45 只算**自建**工具，不含系统那 2 个。全篇凡是提"45 → 19"，都是同一个口径。

### 合并的两条套路

**套路一：开关合成一个布尔参数**

```cpp
// 合并前：self.light.turn_on / self.light.turn_off
// 合并后：
self.light.power(on: true)
```

**套路二：多对象共享一组工具 + id 参数**

```cpp
// 合并前：self.servo1.set_angle / self.servo2.set_angle / ... × 8
// 合并后：
self.servo.set_angle(id: 1, angle: 90)
```

**为什么合并后反而更好用**：语音说"2 号舵机转到 90 度"，模型只需要调用一个工具、填两个参数，比在 8 个同名工具里挑一个更不容易出错。

### 给改造者的三条硬规则

1. **加外设前先算工具数**，超过 32 就得先合并旧的。
2. **能聚合就聚合**，一个类一组工具 + id 参数，是可持续的写法。
3. **纯硬件触发的功能不要注册工具**（比如微动开关控灯，直接在 C++ 里调方法），不占名额。

## 2.8 想改代码，从这三处入手

| 我想… | 改哪里 |
|---|---|
| 换引脚 / 改参数 | `config.h`，只改宏定义 |
| 改外设行为（比如加一种特效） | 对应的 `*_controller.h` 里的 `Render()` 或 `Apply()` |
| 加一个新外设 | 新建一个 header-only 类 + 在 `InitializeTools()` 加一行 |
| 改语音说话的方式 | 对应工具注册处的**描述字符串** |

**不要改**：`main/application.cc`、`main/mcp_server.cc`、`main/display/*`。这些是官方代码，改了以后升级版本会很痛苦。
